# ADR-004 — Bugs encontrados durante sprints de teste/QA/validação seguem fluxo `hotfix/` obrigatório

**Data:** 2026-07-07  
**Status:** Aceita — vigente a partir desta data, não retroativa

---

## Contexto

Durante a Sprint 2.4 (cobertura de regras de negócio de Ordens de Serviço), a investigação do código antes de escrever testes revelou dois bugs reais em produção: `PATCH /api/ordens/<id>/status` aceitava um valor de status desconhecido e o normalizava silenciosamente para "Em andamento" em vez de rejeitar com erro; e `PUT /api/ordens/<id>` sem o campo `status` reabria silenciosamente uma OS Finalizada, apagando `data_finalizado`. Ambos foram corrigidos com aprovação explícita do usuário, mas diretamente na branch da sprint (`test/sprint-2-4-regras-negocio-os`), misturados com os commits de teste planejados.

Isso funcionou, mas expôs um problema de processo à medida que o projeto cresce:

- O histórico da branch mistura trabalho emergencial (correção de bug real) com trabalho planejado (cobertura de teste), dificultando a leitura do log e a revisão em PR.
- A correção só chega a `main`/produção quando a sprint inteira termina e é mergeada — que pode levar dias ou semanas — mesmo sendo um fix de uma linha.
- Não há como reverter a correção isoladamente sem reverter também os testes que a acompanham.
- Não havia critério objetivo para decidir quando um achado justifica parar o trabalho planejado versus apenas documentá-lo para depois.

## Alternativas Avaliadas

### Opção A — Manter o padrão atual: corrigir inline na branch da sprint

**Descrição:** Ao encontrar um bug real durante uma sprint de teste, corrigir diretamente na branch em andamento, em commit separado do trabalho de teste (como feito na Sprint 2.4).

**Prós:**
- Zero overhead de branching — sem trocar de contexto.
- O fix já nasce coberto pelos testes que o revelaram.
- Simples de executar, já era a prática de fato.

**Contras:**
- Histórico mistura emergência com trabalho planejado.
- Fix não chega a `main`/produção até a sprint inteira ser mergeada.
- Revisão de PR precisa separar mentalmente "isso é o bug" de "isso é o teste planejado".
- Reverter o fix isoladamente exige cherry-pick manual.

---

### Opção B — Nunca corrigir durante uma sprint de teste; sempre registrar em `KNOWN_ISSUES.md`

**Descrição:** Qualquer achado durante testes vira entrada em `KNOWN_ISSUES.md`, sem exceção — a correção fica para uma sprint futura dedicada.

**Prós:**
- Escopo da sprint de teste nunca é violado — "sprint de teste é só teste", sem exceções.
- Processo mais simples de enunciar.

**Contras:**
- Bugs com impacto real (corrupção silenciosa de dado, perda de dado, bypass de autorização) continuam ativos em produção por mais tempo do que necessário.
- Contradiz a filosofia do projeto ("dívida técnica é visível" não significa "sempre adiada" quando o achado tem impacto real).
- Já demonstrado insuficiente: os dois bugs da Sprint 2.4 tinham impacto real o bastante para justificar correção imediata.

---

### Opção C — Fluxo `hotfix/` obrigatório, condicionado a critérios objetivos de interrupção (escolhida)

**Descrição:** Ao encontrar um achado durante qualquer sprint de teste, QA ou validação, avaliar contra critérios objetivos (ver `docs/ENGINEERING_GUIDE.md` §11: mutação silenciosa de dado, perda irreversível, bypass de autenticação/autorização, caminho real de produção). Se algum critério for verdadeiro: parar a sprint, abrir `hotfix/<nome>` a partir de `main`, corrigir o mínimo, testar, mergear em `main`, sincronizar a branch da sprint, continuar. Se nenhum critério for verdadeiro: caracterizar via teste e reportar, sem parar.

**Prós:**
- Histórico limpo — cada branch conta uma história (emergência OU trabalho planejado, nunca as duas).
- Fix chega a `main`/produção imediatamente, independente de quando a sprint termina.
- Revisão de PR fica focada — o hotfix é revisado isoladamente, pequeno e óbvio.
- Reverter o fix é trivial (é um commit/PR próprio).
- Critérios objetivos evitam tanto o excesso (parar para qualquer nit) quanto a omissão (ignorar bug real).

**Contras:**
- Overhead de troca de contexto por achado que atende aos critérios.
- Mais branches para gerenciar.
- Exige disciplina — depende de calibrar bem os critérios objetivos (se ficarem rígidos demais, algo sério passa despercebido; se ficarem frouxos demais, a sprint para com frequência excessiva).

---

## Decisão

**Escolhemos: Opção C — fluxo `hotfix/` obrigatório, condicionado aos critérios objetivos de interrupção.**

O fator decisivo foi que a Opção A já provou os dois problemas que motivaram esta ADR (histórico misturado, fix preso na branch da sprint), e a Opção B ignoraria a severidade real de achados como os da Sprint 2.4. A Opção C aceita conscientemente o overhead de branching adicional em troca de um histórico git limpo e correções chegando a produção mais rápido — trade-off que se paga à medida que o projeto cresce e mais colaboradores revisam PRs.

## Consequências

### Positivas

- Histórico git separa claramente correções emergenciais de trabalho planejado.
- Bugs com impacto real chegam a `main`/produção sem esperar o fim da sprint.
- PRs de hotfix são pequenos, focados e fáceis de revisar/reverter isoladamente.

### Negativas / Trade-offs aceitos

- Mais troca de contexto durante sprints de teste/QA/validação quando um achado atende aos critérios.
- Depende da calibração contínua dos critérios objetivos em `ENGINEERING_GUIDE.md` §11 — se se mostrarem mal calibrados (interrupções em excesso ou bugs sérios escapando), revisitar.

### Condições de revisão

- Revisitar se os critérios objetivos gerarem interrupções em excesso (mais de 1 a cada 2-3 sprints de teste) sem achado que realmente justifique.
- Revisitar se um bug com impacto real (mutação silenciosa, perda de dado, bypass de autorização) escapar dos critérios e não gerar hotfix.
- Revisitar quando o pipeline de CI/CD (GitHub Actions, ainda pendente — ver `PROJECT_STATUS.md`) estiver ativo, já que parte deste fluxo pode ser parcialmente automatizada.

### Não retroatividade

Esta política **não se aplica retroativamente**. Os bugs corrigidos nas Sprints 2.2 (KI-012) e 2.4 (validação de `status` em `PATCH`/`PUT /api/ordens`), corrigidos diretamente nas branches das respectivas sprints, **não são reescritos** para se encaixar neste fluxo. A política vale a partir da data de aceitação desta ADR (2026-07-07) para mudanças futuras.
