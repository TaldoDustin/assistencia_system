# ADR-001 — Frontend continuará React + Vite

**Data:** 2026-07-06  
**Status:** Aceita

---

## Contexto

O frontend foi iniciado com React 19 + Vite + Radix UI + Tailwind CSS.
Com a evolução do projeto, avaliou-se migrar para um framework fullstack (Next.js) para simplificar o deploy e eliminar a necessidade de servidor separado para o frontend. O backend Flask já está estável em produção e a equipe tem familiaridade com a separação frontend/backend.

---

## Alternativas Avaliadas

### Opção A — Migrar para Next.js

**Descrição:** Substituir o frontend React + Vite por Next.js com API Routes, eliminando o Flask.

**Prós:**
- Deploy unificado (um único serviço)
- SSR nativo para SEO e carregamento inicial
- TypeScript por default
- Ecossistema Vercel bem integrado

**Contras:**
- Exige reescrever toda a camada de negócio do backend em JavaScript/TypeScript
- Migração do banco de dados para Prisma ou similar
- Perda do código Python maduro em `irflow_os.py`, `irflow_reports.py`, etc.
- Curva de aprendizado considerável

---

### Opção B — Migrar para SvelteKit

**Descrição:** Substituir React por SvelteKit para bundle menor e performance melhor.

**Prós:**
- Bundle significativamente menor
- Sintaxe mais simples que React
- SSR e SSG nativos

**Contras:**
- Sem familiaridade no time
- Ecossistema menor — componentes Radix UI não têm equivalente Svelte
- Reescrita completa do frontend

---

### Opção C — Manter React + Vite (escolhida)

**Descrição:** Manter o frontend atual sem mudança de framework.

**Prós:**
- Zero custo de migração
- Ecossistema React maduro e estável
- Radix UI + Tailwind funcionando bem
- Backend Flask independente e estável

**Contras:**
- Deploy separado (dois serviços)
- Configuração de CORS necessária

---

## Decisão

**Manter React + Vite.**

O custo de migração para Next.js ou SvelteKit supera em muito o benefício. O backend Flask já tem lógica de negócio madura que não seria trivialmente reescrita em JavaScript. O deploy separado (frontend estático + backend Flask) é bem suportado por Fly.io e pelas alternativas documentadas em `DEPLOY.md`.

---

## Consequências

- O build do frontend continua gerando `frontend/dist/` servido pelo Flask em produção.
- Qualquer nova página segue o padrão de arquivos em `frontend/src/pages/`.
- Dependências de UI continuam no ecossistema Radix UI + Tailwind CSS.
- Esta decisão será revisitada se o time crescer e houver demanda por SSR ou TypeScript.

## Amendment (2026-08-16) — shadcn/ui como padrão de composição

**Contexto do amendment:** ao planejar a Fase 1 do Fluxoly Design System
(`docs/engineering/plans/PLAN-design-system-fase1.md`), a investigação do código confirmou que o projeto já
usa, na prática, o padrão estrutural do shadcn/ui — `frontend/src/components/ui/button.jsx` já é escrito no
formato `cva` + `@radix-ui/react-slot` + `cn()`, e `frontend/src/lib/utils.js` já exporta o `cn()` idêntico
ao gerado pelo CLI oficial do shadcn. Isso não era uma decisão registrada — apenas uma convenção que já
havia emergido organicamente no código.

**Decisão do amendment:** o projeto formaliza **shadcn/ui como padrão de composição e implementação dos
componentes de interface**, construído sobre as mesmas primitivas Radix UI já adotadas por este ADR. Não
substitui Radix UI nem reabre a escolha de framework (React + Vite permanece — as "Alternativas Avaliadas"
originais deste ADR não são reconsideradas). shadcn/ui é uma camada de composição sobre a mesma base já
decidida:

```
Radix UI (primitivas acessíveis)
   ↓
shadcn/ui (composição / padrão visual — componentes vivem em frontend/src/components/ui/, editáveis,
não é uma dependência de runtime opaca)
   ↓
Fluxoly Design System (tokens de marca + convenções do projeto)
   ↓
Produto
```

**Consequências do amendment:**
- Componentes novos de interface seguem o padrão shadcn (`cva` para variantes, `cn()` para merge de
  classes, primitiva Radix por baixo quando aplicável) — não uma biblioteca de componentes fechada
  instalada via `npm`.
- Componentes já existentes em `frontend/src/components/ui/` que já seguem esse padrão não são reescritos
  só para "bater" com o output literal do CLI — o padrão importa, não a origem exata do arquivo.
- Ícones passam a ter Phosphor como padrão para componentes novos (ver `PLAN-design-system-fase1.md`),
  coexistindo com `lucide-react` já em uso — não há migração retroativa nesta fase.
- Detalhes de execução (tokens, componentes específicos, Motion, Shell/Dashboard piloto) vivem no plano
  técnico da Fase 1, não neste ADR — este documento registra só a decisão arquitetural.
