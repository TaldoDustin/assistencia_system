# ADR-003 — SQLite continuará sendo utilizado até a versão 2

**Data:** 2026-07-06  
**Status:** Aceita — revisão condicionada a critérios mensuráveis

---

## Contexto

O sistema está em produção com SQLite em modo WAL (Write-Ahead Logging). Cogitou-se migrar para PostgreSQL para obter replicação nativa, conexões concorrentes mais robustas e suporte a tipos mais ricos. Porém, o volume atual de dados e a carga de usuários simultâneos não justificam a complexidade operacional de gerenciar um servidor PostgreSQL dedicado.

---

## Alternativas Avaliadas

### Opção A — Migrar para PostgreSQL

**Descrição:** Substituir SQLite por PostgreSQL, mantendo o Flask e migrando o schema existente.

**Prós:**
- Replicação nativa
- Conexões concorrentes robustas (sem WAL workarounds)
- Tipos de dado mais ricos (JSONB, arrays, etc.)
- Horizontal scaling possível

**Contras:**
- Adiciona infraestrutura: precisa de servidor PostgreSQL em produção
- Custo operacional maior (Fly.io Postgres ou serviço externo)
- Migrations existentes (baseadas em SQLite) precisariam ser reescritas
- Overhead operacional para um volume de dados ainda pequeno

---

### Opção B — SQLite com Litestream

**Descrição:** Manter SQLite + adicionar Litestream para replicação contínua para S3 ou similar.

**Prós:**
- Mantém a simplicidade do SQLite
- Adiciona replicação contínua sem mudança de banco
- Recovery point < 1 segundo (vs. horas com backup manual)
- Custo baixo (armazenamento S3)

**Contras:**
- Adiciona dependência de serviço externo (S3 ou compatível)
- Litestream é uma solução menos madura que PostgreSQL para produção
- Não resolve o problema de múltiplas instâncias

---

### Opção C — Manter SQLite + backup automático (escolhida para v1.x)

**Descrição:** Manter SQLite com WAL mode e confiar no sistema de backup automático existente como mitigação de risco.

**Prós:**
- Zero custo operacional adicional
- Simplicidade total — sem serviço externo
- Deploy mais simples (tudo em um container)
- Volume atual justifica

**Contras:**
- Sem replicação — falha de disco = perda de dados até o último backup
- Não escala para múltiplas instâncias do backend
- Janela de perda de dados: intervalo entre backups

---

## Decisão

**Manter SQLite até a versão 2.0.**

O volume atual e a carga de usuários não justificam a complexidade de PostgreSQL. O backup automático mitiga o principal risco (perda de dados por falha de disco).

**Litestream é a alternativa intermediária preferida** caso os critérios de revisão sejam atingidos antes de uma reescrita completa da camada de dados.

---

## Critérios de Revisão

Esta decisão deve ser revisitada quando qualquer uma das condições abaixo for atingida:

| Condição | Threshold |
|----------|-----------|
| Volume de Ordens de Serviço | > 50.000 registros |
| Usuários simultâneos em pico | > 10 |
| Latência de listagem de OS | > 500ms |
| Necessidade de múltiplas instâncias | Qualquer |
| Incidente de perda de dados | Qualquer |

---

## Consequências

- O backup automático é a principal linha de defesa — deve permanecer operacional e monitorado.
- Migrations devem continuar compatíveis com SQLite (sem tipos ou funções exclusivos do PostgreSQL).
- A camada de acesso ao banco deve ser mantida isolada em funções utilitárias para facilitar migração futura.
- Risco R-01 de `PROJECT_STATUS.md` permanece aceito até a versão 2.
- Toda query nova deve ser testada com `EXPLAIN QUERY PLAN` para garantir uso de índices.
