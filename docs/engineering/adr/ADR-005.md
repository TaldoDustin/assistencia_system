# ADR-005 — Estratégia de Multiempresa

**Data:** 2026-07-08
**Status:** PROPOSTA — alternativas avaliadas tecnicamente, decisão final pendente do Product Owner
**Autores:** Claude (análise técnica) — decisão a ser preenchida pelo Product Owner

---

## Contexto

O plano de produto (ver `PRODUCT_REQUIREMENTS.md` e discussão de roadmap comercial) inclui suporte a
múltiplas empresas/clientes usando a mesma instalação do sistema, cada uma com seus próprios usuários,
Ordens de Serviço, clientes, estoque e configurações isoladas entre si.

Hoje o sistema é single-tenant: uma instância = uma empresa, um banco SQLite único (`database.db`),
sem nenhum conceito de `empresa_id` ou isolamento de dados no schema (ver `docs/engineering/DATABASE.md`).

Esta decisão precisa ser tomada **antes** de qualquer domínio novo (Vendas, Caixa, Financeiro) ser
implementado, porque a estratégia escolhida afeta a forma como toda tabela nova deve ser desenhada desde
o início. Decidir depois significa migração retroativa de todo o schema construído no meio tempo.

**Importante:** esta ADR registra apenas a decisão de estratégia. A implementação de multiempresa em si
continua planejada para a Fase de Escala (fora do escopo do MVP comercial) — ver critérios de aprovação em
`CLAUDE.md` ("Requer aprovação explícita + ADR documentado").

---

## Alternativas Avaliadas

### Opção A — Um banco (arquivo SQLite) por empresa

**Descrição:** Cada empresa tem seu próprio arquivo `database_<empresa>.db`. A aplicação seleciona qual
banco conectar com base no domínio/subdomínio ou empresa autenticada.

**Prós:**
- Isolamento físico total — impossível uma query vazar dado de outra empresa por bug de filtro esquecido
- Backup por empresa é trivial (copiar um arquivo)
- Migração de uma empresa para outro servidor é trivial (mover um arquivo)
- Compatível com a decisão atual de manter SQLite (ADR-003) sem mudança de banco

**Contras:**
- N empresas = N conexões/arquivos para gerenciar, migrar e monitorar — operação escala linearmente com o número de clientes
- Relatórios cross-empresa (ex.: métricas agregadas para o próprio time da Fluxoly) exigem abrir N bancos
- `app.py` hoje assume um único caminho de banco fixo (`IR_FLOW_DATA_DIR`) — exigiria uma camada de resolução de tenant antes de qualquer conexão

---

### Opção B — Coluna `empresa_id` em todas as tabelas (single database, shared schema)

**Descrição:** Um único banco. Toda tabela relevante (`os`, `estoque`, `usuarios`, `shopping_list`, etc.)
ganha uma coluna `empresa_id`, e toda query passa a filtrar por ela.

**Prós:**
- Um único banco para operar, fazer backup e monitorar
- Relatórios cross-empresa são triviais (a própria empresa administradora)
- Mudança incremental: adicionar coluna é aditivo, compatível com a regra de migrations do `ENGINEERING_GUIDE.md` seção 5

**Contras:**
- Isolamento depende 100% de disciplina de código — **qualquer query que esqueça o filtro `WHERE empresa_id = ?`
  vaza dado de uma empresa para outra**. Isso é exatamente o tipo de achado que se enquadraria em C-03
  (bypass de autorização) do `ENGINEERING_GUIDE.md` seção 11 se acontecer em produção
- Precisa de um mecanismo central que garanta o filtro sempre (ex.: middleware, wrapper de query, ou
  camada de repository obrigatória — ver convenção de domínios na seção 3.1 do `ENGINEERING_GUIDE.md`)
- SQLite não tem Row-Level Security nativo (diferente de PostgreSQL) — a garantia teria que ser 100%
  na camada de aplicação, sem rede de segurança do banco

---

### Opção C — Schema por empresa (multi-schema)

**Descrição:** Um único servidor de banco, um schema separado por empresa.

**Prós:**
- Isolamento mais forte que Opção B, sem o custo operacional de N arquivos da Opção A

**Contras:**
- **SQLite não suporta múltiplos schemas da forma como PostgreSQL/MySQL suportam** — a alternativa mais
  próxima em SQLite seria `ATTACH DATABASE`, que tem limitações de concorrência e não é o padrão de uso
  da biblioteca. Essa opção, na prática, exigiria migrar para PostgreSQL antes de ser viável — o que
  reabriria a decisão já tomada em ADR-003 (SQLite até a versão 2.0)
- Maior complexidade operacional que as opções A e B, sem ganho claro sobre elas dado o estágio atual do projeto

---

## Recomendação Técnica

Entre as três, a **Opção A (banco por empresa)** é a que menos depende de disciplina perfeita de código
para garantir isolamento — e isolamento entre dados de clientes diferentes é o tipo de falha que, se
acontecer, é crítica por definição (C-03) e afeta a confiança comercial no produto inteiro, não só uma
empresa.

A **Opção B (`empresa_id`)** é viável e mais barata operacionalmente, mas só deve ser considerada segura
se acompanhada de um mecanismo central de enforcement (não apenas convenção de código) — por exemplo,
toda query de domínio passando obrigatoriamente por uma função de repository que injeta o filtro, nunca
SQL solto no controller/service.

A **Opção C** só faz sentido se o projeto já tivesse decidido migrar para PostgreSQL — o que contraria
ADR-003 no estágio atual. Não recomendada enquanto essa condição não mudar.

Esta é uma recomendação técnica, não a decisão. O fator decisivo real depende de informação de negócio
que a engenharia não tem: custo tolerável de infraestrutura por empresa, volume esperado de clientes
simultâneos, e se relatórios cross-empresa são uma necessidade do próprio negócio da Fluxoly.
