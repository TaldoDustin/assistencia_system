# ADR-008 — Rebranding técnico incremental: novos módulos nascem como `fluxoly_*`

**Data:** 2026-07-27
**Status:** Aceita
**Autores:** Usuário (CTO) — decisão de nomenclatura técnica; Claude — mapeamento de impacto e execução

---

## Contexto

`docs/company/BRAND_IDENTITY.md` V1.0 e `ADR-006` (2026-07-10) já consolidaram a transição de marca
"Assistência System" → "Fluxoly" na camada de negócio e documentação. A camada de código nunca foi
tocada — `ADR-006` seção "Decisão 2" já registrava isso deliberadamente como fora de escopo, deixando
para "janela de manutenção planejada antes do lançamento comercial".

Hoje o nome legado (`irflow_*`, `IR_FLOW_*`) aparece em três camadas distintas, com blast radius
diferente cada uma:

1. **Código-fonte** — `irflow_blueprints_api.py`, `irflow_clientes_service.py`,
   `irflow_unidades_serializadas_*.py`, etc.
2. **Infraestrutura/variáveis de ambiente** — `irflow_logging.py`, `irflow_storage.py`,
   `IR_FLOW_DATA_DIR`, `IR_FLOW_DEBUG_CONN_TRACE`, etc.
3. **Repositório/domínio de produção** — nome do repositório Git, `assistencia-system.fly.dev` (legado,
   hospedagem já migrou para Render/Vercel mas o slug não).

Com o início do Épico Vendas — o primeiro domínio de negócio novo desde a adoção oficial da marca
Fluxoly — surge a pergunta concreta: o módulo novo (`irflow_vendas_service.py`, seguindo a convenção
existente de `ENGINEERING_GUIDE.md` §3.1) nasce com o nome legado, ou já nasce com o nome da marca?

Continuar nascendo como `irflow_*` significa que o nome antigo continua se expandindo pelo código
precisamente no momento em que a plataforma está assumindo definitivamente a identidade Fluxoly.

---

## Alternativas Avaliadas

### Opção A — Manter `irflow_*` para tudo até um rebranding técnico completo

**Descrição:** Não mudar nada agora; código novo continua nascendo com o prefixo legado até uma sprint
dedicada de rebranding cobrir tudo de uma vez (código + infra + variáveis de ambiente + repositório).

**Prós:**
- Zero decisão a tomar agora; nenhuma inconsistência de nomenclatura dentro do código no curto prazo.

**Contras:**
- Todo código novo (Vendas, e os domínios seguintes do roadmap) aumenta a superfície que uma futura
  sprint de rebranding precisará tocar — dívida técnica crescendo ativamente, não estática.
- Adia indefinidamente uma decisão que já está madura (marca já é oficialmente Fluxoly desde 2026-07-10).

### Opção B — Rebranding técnico completo agora (código + infra + variáveis de ambiente + repositório)

**Descrição:** Executar de uma vez a migração completa de nomenclatura em todas as três camadas.

**Prós:**
- Resolve a dívida de uma vez, sem nomenclatura mista permanente.

**Contras:**
- Risco desproporcional ao momento: toca imports, testes, Docker, CI, deploy, variáveis de ambiente em
  produção, backups — tudo simultaneamente, sem necessidade de negócio imediata (não é isso que o
  Épico Vendas pede).
- Mistura uma mudança de infraestrutura ampla com o início de uma feature de negócio prioritária — viola
  a regra do projeto de não misturar refactor com feature.

### Opção C — Transição incremental: só módulos novos nascem como `fluxoly_*` (escolhida)

**Descrição:** A partir de agora, todo módulo novo (controller/service/repository de um domínio ainda
não implementado) nasce com o prefixo `fluxoly_`. Módulos legados existentes (`irflow_*`) permanecem
inalterados — nenhum rename retroativo nesta decisão. Um "Épico de Rebranding Técnico" futuro (não
escopado, não agendado) cobre eventualmente código legado, infraestrutura e variáveis de ambiente, em
sprints próprias (documentação → módulos novos [esta decisão] → infraestrutura → variáveis de ambiente
com compatibilidade temporária → remoção do legado).

**Prós:**
- Risco zero para o código legado — nada existente é tocado.
- Para a dívida técnica de crescer: a partir de hoje, nenhum nome novo usa o prefixo antigo.
- Decisão pequena, reversível e imediatamente aplicável ao Épico Vendas sem atrasar seu início.

**Contras:**
- Nomenclatura mista (`irflow_*` legado convivendo com `fluxoly_*` novo) por tempo indeterminado — mesmo
  trade-off já aceito conscientemente em `ADR-006` para a documentação/marca.

---

## Decisão

**Escolhemos: Opção C.**

A partir desta decisão, qualquer módulo novo (domínio de negócio ainda não implementado) segue a
convenção de `ENGINEERING_GUIDE.md` §3.1 com o prefixo `fluxoly_` em vez de `irflow_`:
`fluxoly_<dominio>_controller.py` / `_service.py` / `_repository.py`. O Épico Vendas é o primeiro a
aplicar esta regra (`fluxoly_vendas_controller.py`/`_service.py`/`_repository.py`).

Módulos legados (`irflow_*`) **não são renomeados** nesta decisão — permanecem como estão até um Épico
de Rebranding Técnico futuro, ainda não escopado nem agendado, que cobriria (nesta ordem sugerida, não
comprometida): documentação restante → infraestrutura (`irflow_logging.py` → `fluxoly_logging.py`,
etc., com aliases temporários) → variáveis de ambiente (`FLUXOLY_*` com fallback para `IR_FLOW_*`) →
remoção do legado quando não houver mais consumidores. Registrado como dívida técnica (TD-12,
`docs/operations/PROJECT_STATUS.md`), sem compromisso de prazo.

O stub `irflow_vendas_service.py` (criado na Sprint 3 Unidade 7 como placeholder, nunca importado nem
instanciado) é removido nesta decisão — substituído pelos módulos reais `fluxoly_vendas_*.py`. Não é
uma remoção de código em uso: confirmado que o arquivo é só docstring, sem rota/tabela/wiring.

---

## Consequências

### Positivas

- A dívida de nomenclatura para de crescer a partir de hoje — todo domínio novo já nasce com o nome
  definitivo da plataforma.
- Nenhum risco introduzido no código legado — zero mudança de import, teste ou comportamento existente.
- Decisão pequena e imediatamente reversível se necessário (nenhum código legado depende do prefixo
  novo).

### Negativas / Trade-offs aceitos

- Convivência de dois prefixos (`irflow_*` legado, `fluxoly_*` novo) no repositório por tempo
  indeterminado — um novo colaborador (humano ou agente de IA) precisa saber que ambos coexistem por
  decisão deliberada, não por inconsistência acidental. Este ADR existe justamente para essa
  rastreabilidade.
- `ENGINEERING_GUIDE.md` §3.1 precisa de nota explícita sobre os dois prefixos, para não confundir a
  convenção de camadas (controller/service/repository, inalterada) com a convenção de nomenclatura
  (alterada só para módulos novos).

### Condições de revisão

Revisitar quando o Épico de Rebranding Técnico completo for priorizado — nesse momento, decidir o
escopo real de R1-R5 (documentação → infra → variáveis de ambiente → remoção do legado) como uma
decisão própria, não comprometida por este ADR.

## Atualização (2026-07-31) — Sprint Housekeeping, estratégia de rename dos módulos `.py`

O Épico de Rebranding Técnico citado nas "Condições de revisão" acima foi priorizado (Sprint
Housekeeping, TD-12). Ao planejar a Fase 4 (`docs/operations/SPRINTS/SPRINT_HOUSEKEEPING.md`,
`docs/engineering/audits/AUDIT_DEPENDENCIES.md`), esta ADR foi revisitada: a "Decisão" original citava
`irflow_logging.py` → `fluxoly_logging.py` como exemplo de rename **com alias temporário**. Decisão
tomada agora, especificamente para os módulos de baixo risco (classificados 🟢 em
`AUDIT_DEPENDENCIES.md` — poucas dependências, todas mapeadas de forma exaustiva via `git grep`, não
por amostragem):

**Rename direto, sem alias temporário**, para os módulos 🟢. Razão: o alias existe para proteger contra
consumidores não mapeados; para estes módulos, `AUDIT_DEPENDENCIES.md` já enumerou exaustivamente quem
importa cada um (não uma estimativa) — o risco que o alias mitigaria já foi eliminado pela auditoria.
Um shim temporário adicionaria um arquivo por módulo para lembrar de remover depois, sem proteção real
adicional neste caso específico.

Isto **não revoga** a recomendação de alias/fallback da decisão original para os itens de maior risco
ou fora do controle direto do repositório — módulos-hub (`irflow_core.py`, `irflow_os.py`, ainda a
decidir na execução do Lote 4) e, principalmente, as variáveis de ambiente `IR_FLOW_*` (onde o alias
via `FLUXOLY_*` com fallback para `IR_FLOW_*` continua sendo a estratégia planejada, já que essas
variáveis dependem de configuração externa no Render, fora do controle do `git grep`).

Decisão confirmada pelo usuário (CTO) em 2026-07-31, respondendo à pergunta direta sobre divergir desta
ADR antes de executar o Lote 2 da Sprint Housekeeping.
