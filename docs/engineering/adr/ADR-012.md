# ADR-012 — Ambiente de Demonstração/Homologação: arquitetura dedicada e isolamento de credenciais

**Data:** 2026-08-11
**Status:** Aceita
**Autores:** Isaque Souza (CTO/Product Architect), Claude Code

---

## Contexto

O `RELEASE_1.0_MASTER_CHECKLIST.md` lista "Ambiente de demonstração" como um dos 4 itens ainda em ❌ (zero trabalho iniciado) — um bloqueador real da Release 1.0, pré-requisito da Fase 1 do `GO_LIVE_PLAN.md` (cliente conhecer o sistema antes do go-live) e, por consequência, do próprio item "Cliente piloto homologado".

Duas Discoveries somente-leitura precederam esta decisão, em 2026-08-11:

1. **Discovery da Parte C da Release 1.0** — mapeou os 4 bloqueadores reais (LGPD, Manual do usuário, Ambiente de demonstração, Cliente piloto) e recomendou o Ambiente de Demonstração como a próxima frente, por ser o único puramente técnico — não depende de decisão de produto/jurídica prévia, ao contrário de LGPD.
2. **Discovery dedicada do Ambiente de Demonstração/Homologação** — cruzou `GO_LIVE_PLAN.md`, `KNOWN_ISSUES.md` (KI-029, KI-037), o código real da implementação de Preview Seguro (`IS_PULL_REQUEST`, guards em `fluxoly_config.py`/`app.py`) e a configuração de infraestrutura (CORS, Render, Vercel, Sentry).

Essa segunda Discovery trouxe um achado que muda o cálculo de risco em relação ao que foi aceito no Dry-Run 2B: o **INC-003** (um Render PR Preview herdou credenciais/configuração de produção e disparou a integração MercadoPhone real, importando 405 OS reais para o banco do preview) teve como causa raiz a **herança automática de variáveis de ambiente** na criação de um recurso Render novo — não uma falha de isolamento físico de disco. O **KI-037** (endpoints manuais do MercadoPhone sem guard de preview) foi aceito como risco residual no Dry-Run 2B porque a mitigação operacional usada foi *não utilizar sessão admin/técnico real* dentro do preview. Um ambiente de demonstração, por definição, **exige** sessão admin/técnico real para que um prospect opere o sistema — a mitigação que sustentou a aceitação do KI-037 no Dry-Run 2B não se sustenta aqui.

Custo de não decidir: sem uma arquitetura formalmente aprovada, qualquer tentativa de provisionar o ambiente reproduziria o risco do INC-003 por tentativa-e-erro em vez de por design.

---

## Princípio central

O Ambiente de Demonstração **não é** um PR Preview permanente e **não é** uma cópia da produção. É um terceiro ambiente, com identidade própria, isolado por design — nunca por acidente de configuração.

```
                    ┌────────────────────┐
                    │     PRODUÇÃO       │
                    │ Render + Vercel    │
                    │ Dados reais        │
                    └─────────┬──────────┘
                              │
                        totalmente
                         isolado
                              │
                    ┌─────────▼──────────┐
                    │       DEMO         │
                    │ Render + Vercel    │
                    │ Dados sintéticos   │
                    │ Credenciais próprias│
                    └────────────────────┘

PR Preview
    │
    └── continua sendo ambiente efêmero,
        separado do Demo (não reaproveitado)
```

O código passa a reconhecer quatro ambientes distintos: `production`, `demo`, `preview`, `development` — cada um com comportamento explícito, em vez de o Demo herdar o comportamento de outro ambiente por conveniência.

## Alternativas Avaliadas

### Questão 1 — Topologia de infraestrutura

#### Opção A — Reaproveitar o mecanismo de PR Preview como ambiente permanente

**Descrição:** Manter um PR aberto indefinidamente para obter automaticamente `IS_PULL_REQUEST=true` e toda a defesa em profundidade do Preview Seguro já implementada.

**Prós:**
- Zero código novo — o guard de segurança já existe e já foi validado no Dry-Run 2B

**Contras:**
- Semanticamente incorreto: um ambiente persistente e operacional modelado como um artefato efêmero
- Previews herdam automaticamente as variáveis do serviço-base na criação — a mesma causa-raiz do INC-003 — exigindo a mesma checagem manual a cada recriação
- Não documentado como padrão suportado para uso não-efêmero

#### Opção B — Serviço Render dedicado + projeto Vercel dedicado (escolhida)

**Descrição:** Provisionar um Web Service Render novo (com disco próprio) e um projeto Vercel novo, independentes de qualquer PR.

**Prós:**
- Persistente, com nome/domínio próprios, sem depender de um PR permanentemente aberto
- Isolamento físico de disco/banco automático — mesmo padrão que já provou funcionar entre produção e previews
- Mais fácil de operar e explicar do que um "PR permanente"

**Contras:**
- Não recebe `IS_PULL_REQUEST=true` automaticamente — exige mecanismo próprio de identificação (Questão 2)
- Novo serviço = novo custo fixo (não estimado nesta ADR — depende de tabela de preço vigente Render/Vercel, a validar no Plano Técnico)

---

### Questão 2 — Identificação do ambiente para o guard de segurança e observabilidade

#### Opção A — Setar `IS_PULL_REQUEST=true` manualmente no serviço demo

**Descrição:** Forçar a variável que hoje só o Render seta automaticamente em Previews, reaproveitando 100% do guard existente sem escrever código novo.

**Prós:**
- Reaproveita a defesa em profundidade já testada sem nenhuma mudança de código

**Contras:**
- Rotula o ambiente demo como "preview" em logs e no Sentry, confundindo qualquer investigação futura que precise distinguir PR Preview real de ambiente demo
- Semântica incorreta se perpetua à medida que o sistema cresce

#### Opção B — Nova variável `IR_FLOW_ENVIRONMENT=demo` (escolhida)

**Descrição:** Introduzir uma flag de ambiente própria, seguindo a convenção de nomenclatura já estabelecida na `ADR-008` (módulos/config novos nascem com prefixo `IR_FLOW_*`/`fluxoly_*`). O código passa a reconhecer `production`, `demo`, `preview`, `development` como valores distintos.

**Prós:**
- Semântica correta — Sentry, logs e qualquer guard futuro distinguem o Demo de um Preview real
- Consistente com a convenção de nomenclatura já em uso no projeto

**Contras:**
- É mudança de código (não apenas configuração) — sai do escopo desta ADR e entra explicitamente no escopo do Plano Técnico seguinte

---

## Decisão

**Escolhemos: Opção B em ambas as questões** — serviço Render dedicado, identificado por uma flag de ambiente própria (`IR_FLOW_ENVIRONMENT=demo`), nunca por reaproveitamento do mecanismo de PR Preview.

A baseline arquitetural completa, com as 9 decisões fechadas nesta Discovery, fica registrada como:

| # | Decisão | Posição aprovada |
|---|---|---|
| 1 | Topologia | Render dedicado (Web Service + disco próprio) + projeto Vercel dedicado |
| 2 | Identificação do ambiente | Nova flag `IR_FLOW_ENVIRONMENT=demo` — escopo de código do Plano Técnico |
| 3 | KI-037 | Bloqueante — corrigido antes de qualquer acesso externo ao ambiente Demo |
| 4 | Dados | Seed sintético de "loja modelo" realista, 100% fictício — nunca dump/importação de produção (lição do KI-029) e nunca importação real via MercadoPhone |
| 5 | Contas | Fixas e próprias do ambiente (`admin.demo`, `tecnico.demo`, `vendedor.demo`), nunca compartilhadas com produção |
| 6 | Reset | Manual sob demanda — automação (ex. Render Cron) só se o uso demonstrar necessidade |
| 7 | Domínio | Subdomínio padrão Vercel/Render (`*.vercel.app` / `*.onrender.com`) — domínio próprio fica para decisão futura de branding/custo |
| 8 | Acesso | Login normal da aplicação confirmado; camada adicional de controle de acesso **deliberadamente deferida** ao Plano Técnico, após avaliação de custo/complexidade |
| 9 | Homologação | Definition of Done de 14 critérios (abaixo), como gate de "ambiente homologado" |

### Regra explícita de isolamento de credenciais

O ambiente Demo **nunca** deve receber credenciais de integração de produção por herança automática de configuração — a causa raiz exata do INC-003. Isso vale para toda integração externa presente ou futura: MercadoPhone, e-mail, Google Drive, Sentry, e qualquer nova integração que o sistema venha a ter. A criação do serviço Demo no Render **não pode ser feita por "duplicar serviço"** a partir da produção — cada variável de ambiente (incluindo uma `FLASK_SECRET_KEY` própria, gerada nova) deve ser configurada explicitamente, uma a uma.

### Definition of Done — ambiente homologado (critério #9)

- [ ] Admin consegue entrar
- [ ] Técnico consegue entrar
- [ ] Vendedor consegue entrar
- [ ] Dados são 100% sintéticos
- [ ] Nenhuma credencial de produção está presente
- [ ] MercadoPhone não é acessível
- [ ] Endpoints manuais do KI-037 não conseguem atingir a integração real
- [ ] Backup não envia dados para destino real
- [ ] Sentry identifica corretamente `environment=demo`
- [ ] CORS funciona com o domínio Vercel do Demo
- [ ] Sessão cross-site funciona entre frontend e backend do Demo
- [ ] Reset restaura o estado inicial
- [ ] Demo não compartilha banco nem disco com produção
- [ ] Produção permanece intocada durante todos os testes acima

## Consequências

### Positivas

- A Release 1.0 ganha uma arquitetura aprovada para o único bloqueador puramente técnico entre os 4 identificados na Discovery da Parte C, desbloqueando o caminho até o Cliente Piloto
- KI-037 deixa de ser um risco residual silenciosamente aceito e passa a ter status de bloqueador formal — reduz a chance de o mesmo padrão de risco do INC-003 se repetir, agora com um humano externo à equipe
- A regra de isolamento de credenciais fica registrada de forma reutilizável para qualquer ambiente futuro (não só o Demo), aplicando a lição do INC-003 de forma preventiva
- `IR_FLOW_ENVIRONMENT` estabelece um vocabulário de ambiente explícito (`production`/`demo`/`preview`/`development`) reutilizável por qualquer guard ou instrumentação futura

### Negativas / Trade-offs aceitos

- Novo custo fixo de infraestrutura (Render + Vercel dedicados) — magnitude não estimada nesta ADR, a levantar no Plano Técnico
- O item #8 (camada adicional de acesso) fica sem decisão fechada — risco aceito conscientemente de reabrir essa discussão no Plano Técnico
- KI-037 vira dependência bloqueante do cronograma do Ambiente Demo — o Plano Técnico não pode tratar o Demo como entregável isolado da correção desse KI

### Condições de revisão

- Se o volume de uso do Demo justificar, revisitar a decisão de reset manual (#6) para automação
- Se a demonstração exigir domínio de marca (branding), revisitar a decisão de domínio padrão (#7)
- Revisitar a decisão de acesso (#8) obrigatoriamente dentro do Plano Técnico, não depois
