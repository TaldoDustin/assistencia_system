# ADR-012 — Track paralelo Next.js para modernização de frontend (não-produção)

**Data:** 2026-08-04
**Status:** ACEITA — escopo restrito (ver "Decisão")
**Autores:** Claude (análise técnica) — decisão de negócio confirmada pelo usuário (CTO)

---

## Contexto

O CTO trouxe uma proposta de arquitetura completa para o Fluxoly, inspirada em produtos SaaS de
referência (Linear, Stripe, Vercel, Notion, Clerk, Framer, Raycast, Figma): frontend em Next.js +
TypeScript + TailwindCSS + shadcn/ui + Motion/GSAP/Anime.js/Three.js, banco PostgreSQL via Supabase,
autenticação via BetterAuth, e-mail via Resend, storage via Supabase Storage, push via Firebase Cloud
Messaging, e um roadmap de 5 fases culminando em SaaS multiempresa com billing via Stripe.

Essa proposta colide diretamente com três decisões já registradas:

- **ADR-001** (Frontend continuará React + Vite, 2026-07-06) — rejeitou Next.js explicitamente, mas a
  própria ADR já previa a condição de revisão: *"Esta decisão será revisitada se o time crescer e
  houver demanda por SSR ou TypeScript."* A demanda por TypeScript é exatamente o que motiva esta ADR.
- **ADR-003** (SQLite até a versão 2.0, 2026-07-06) — a migração para PostgreSQL/Supabase proposta
  reabriria essa decisão diretamente.
- **ADR-005** (Estratégia de Multiempresa, PROPOSTA, decisão pendente do Product Owner) — o pivot para
  billing/Stripe da proposta original depende diretamente da decisão de negócio que essa ADR ainda não
  tem.

Além disso, o sistema está em produção com clientes reais, `TD-01` (decomposição de
`fluxoly_blueprints_api.py`) está em andamento, e o `RELEASE_STRATEGY.md` (decidido em 2026-07-25) tem o
projeto hoje na **Fase 1 — Release 1.0 (primeiro cliente pagante)**, com "Infraestrutura SaaS" e
"Multiempresa" reservadas para as Fases 2 e 3, depois — não durante.

Perguntas de sequenciamento e escopo foram levadas ao CTO antes de qualquer plano técnico, com as
respostas registradas na seção "Decisão" abaixo.

---

## Alternativas Avaliadas

### Opção A — Adotar a proposta completa agora, substituindo Flask/SQLite/auth própria

**Descrição:** Reescrita total: Next.js substitui Vite+React, backend migra parcial ou totalmente para
Next.js API Routes, banco migra para Postgres/Supabase, autenticação própria é substituída por
BetterAuth, e-mail/storage/push passam para os novos vendors, multiempresa e billing entram em escopo
ativo.

**Prós:**
- Stack unificada, moderna, alinhada à visão de longo prazo do CTO
- Resolve de uma vez todas as decisões pendentes (ADR-001, ADR-003, ADR-005)

**Contras:**
- Reabre 3 ADRs simultaneamente sem isolar o risco de nenhuma delas
- Migração de banco com clientes reais em produção (`o banco é sagrado`) sem plano de rollback dedicado
- Interrompe `TD-01` e a corrida pela Fase 1 (primeiro cliente pagante) já em andamento
- Prejulga a decisão de negócio da ADR-005 (multiempresa/billing) embutindo-a como premissa técnica

---

### Opção B — Não mexer em nada agora; revisitar só quando os gatilhos da ADR-003 forem atingidos

**Descrição:** Manter o status quo (React+Vite, Flask, SQLite) até que as condições de revisão já
documentadas na ADR-003 (volume de OS, usuários simultâneos, latência) sejam atingidas.

**Prós:**
- Zero risco adicional, zero desvio de foco da Fase 1

**Contras:**
- Ignora a demanda real por TypeScript/SSR que a própria ADR-001 já previa como gatilho de revisão
- Adia indefinidamente a modernização de UI, mesmo em uma frente que não teria custo de produção

---

### Opção C — Track paralelo, escopo frontend-only, não-produção (escolhida)

**Descrição:** Um novo diretório/prototype Next.js + TypeScript + Tailwind + shadcn/ui + Phosphor Icons +
Motion é desenvolvido em paralelo, consumindo a API Flask existente (mesmos endpoints já em produção),
sem tocar banco, autenticação, e-mail, storage, push ou multiempresa/billing. Backend, banco e o
frontend Vite+React em produção continuam intocados e servindo clientes normalmente durante todo o
track. `TD-01` e a Fase 1 continuam sem interrupção.

**Prós:**
- Isola o risco: nenhuma mudança em produção, nenhum dado de cliente em risco
- Responde à condição de revisão já prevista na própria ADR-001 sem reabrir ADR-003 ou ADR-005
- Permite validar a stack nova (Next.js/shadcn/Motion) contra telas reais antes de qualquer decisão de
  substituir produção
- Compatível com o próprio texto da proposta do CTO ("Backend: Flask (fase atual)")

**Contras:**
- Duas bases de frontend coexistem temporariamente (custo de manutenção, mas nenhuma delas é descartada
  às pressas)
- Autenticação do protótipo precisa de uma solução ponte (ver "Pontos em aberto") até uma decisão futura
  sobre BetterAuth fazer sentido (que depende de o backend migrar para Node/Next.js — fora de escopo aqui)

---

## Decisão

**Opção C.** Confirmada pelo CTO em três perguntas diretas (2026-08-04):

1. **Sequenciamento:** track roda **agora, em paralelo** — não pausa `TD-01` nem a Fase 1 (Release 1.0,
   primeiro cliente pagante) no stack atual.
2. **Escopo imediato ("Fase 1 — Fundação" da proposta original):** **só frontend**. Backend Flask e
   banco SQLite continuam intocados; nenhuma migração de banco começa aqui. Isso mantém a ADR-003 válida
   sem alteração.
3. **Multiempresa/billing:** **ainda visão de longo prazo**. A ADR-005 continua PROPOSTA, sem decisão de
   negócio tomada nesta ADR. Nenhum trabalho de Stripe/billing/multiempresa entra em escopo agora.

Como consequência direta do item 1, esta ADR **revisa parcialmente a ADR-001**: Next.js deixa de ser
"rejeitado" e passa a ser adotado como track de avaliação ativo — mas React + Vite continua sendo o
frontend **de produção** até uma ADR futura decidir formalmente substituí-lo (o que exigiria, no mínimo,
o track paralelo comprovar viabilidade e uma decisão explícita de corte de produção).

### Pontos em aberto, deliberadamente fora do escopo desta ADR

- **BetterAuth:** exige backend próprio (Node/Next.js API routes + tabelas de sessão/usuário). Como o
  backend continua Flask, adotar BetterAuth agora criaria uma segunda fonte de verdade de autenticação
  coexistindo com a atual — não é seguro nem necessário nesta fase. O protótipo Next.js consome a API
  Flask existente; a estratégia de sessão para o protótipo (proxy de cookie de sessão Flask vs. login
  próprio de teste) é decisão técnica da implementação, não desta ADR.
- **Resend, Supabase Storage, Firebase Cloud Messaging:** todos são integrações do lado do backend.
  Ficam fora de escopo enquanto o backend for Flask — não fazem parte da "Fase 1 — Fundação" deste track.
- **Observabilidade adicional (Cloudflare, Upstash, Sentry extra, OpenTelemetry, Better Stack), SEO/Search
  Console, IA/MCP:** não avaliados nesta ADR — pertencem a fases muito posteriores da proposta original e
  não têm relação com o escopo frontend-only decidido aqui.

Ver plano de execução detalhado em `docs/operations/SPRINTS/SPRINT_NEXTJS_FUNDACAO.md`.

---

## Consequências

### Positivas

- Nenhum risco introduzido em produção — clientes reais não são afetados durante todo o track
- Resposta concreta à condição de revisão que a própria ADR-001 já previa
- Decisão de substituir produção (se vier a acontecer) será tomada com um protótipo real para avaliar,
  não em abstrato

### Negativas / Trade-offs aceitos

- Duas bases de frontend coexistem temporariamente — custo de contexto para quem alternar entre elas
- Nenhuma integração de auth/e-mail/storage/push nova entra nesta fase, mesmo que a proposta original as
  quisesse desde já — adiado até (e se) o backend migrar

### Condições de revisão

- Revisitar esta ADR quando o track paralelo tiver um conjunto representativo de telas prototipadas
  (ver critérios de aceitação da Sprint) — decisão então: promover a produção, manter como track
  permanente de exploração, ou descontinuar
- Revisitar ADR-003 e ADR-005 apenas quando/se o CTO tomar a decisão de negócio correspondente — esta ADR
  não antecipa nenhuma delas
