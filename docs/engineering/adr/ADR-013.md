# ADR-013 — "Lista de Aparelhos Disponíveis": app standalone, fonte MercadoPhone (API nova), acesso em 2 níveis por senha

**Data:** 2026-09-03
**Status:** Aceita — aprovada pelo CTO em 2026-09-03
**Autores:** Isaque Souza (CTO), Claude Code

---

## Contexto

A Discovery `docs/product/research/DISCOVERY_LISTA_PRECOS_PUBLICA.md` (aprovada 2026-09-03, BR-070 a
BR-078) fechou **o quê**: uma ferramenta **interna** de consulta ao estoque de aparelhos da loja
IR Phones, com duas áreas atrás de senha —

- **Geral** (vendedores): modelo, armazenamento, cor, estado, saúde de bateria, preço de venda,
  disponibilidade. Sem custo, sem PII.
- **Estoque** (organizador): tudo da Geral + custo/margem/dias em estoque + a ação de **reservar** uma
  unidade (que a tira da Geral e a joga na lista "Reservados").

Restam decisões **de arquitetura** que a Discovery deliberadamente não tomou (ADR-010, Princípio da
Separação de Decisões): onde o app vive, de onde vêm os dados, como o acesso de 2 níveis é imposto, e
onde mora o estado da reserva — já que o MercadoPhone **não tem** status "Reservado" (confirmado via
`GET /api/v1/catalog/availability`: só 4 situações).

Fatos técnicos levantados na Discovery (com o token da API, 2026-09-03):

- Existe uma **API nova documentada** do MercadoPhone — `platform.mercadophone.tech`, header
  `X-API-Key` — distinta da API legada (só OS) que `fluxoly_mercadophone.py` usa hoje.
  `GET /api/v1/inventory` é paginado, self-describing (`gbDescricao`/`corDescricao`/
  `estadoProdutoDescricao`/`saudeBateria`/`valorVenda`/`valorCusto`), e **só de leitura** — não há
  `PUT`/`PATCH`/`DELETE` nem endpoint de reserva.
- O payload traz **dado sensível**: `valorCusto`, `fornecedorNome`, `clienteNome`/`clienteId` (nome
  completo de quem vendeu o aparelho à loja), campos fiscais.

Custo de não decidir: provisionar por tentativa-e-erro arriscaria repetir o padrão do INC-003 (uma
credencial de terceiro herdada/exposta onde não devia) e enterrar decisões de produto dentro de
escolhas de implementação.

---

## Princípio central

A ferramenta **não faz parte do monólito Fluxoly** e **não toca** `app.py`, o banco `database.db`, nem
os projetos Render/Vercel de produção ou de Demo. É um app pequeno e isolado, com identidade,
credencial e deploy próprios. A fonte de verdade é o MercadoPhone; o Fluxoly-plataforma não intermedia.

```
   MercadoPhone (API nova, X-API-Key)  ──leitura──►  App "estoque.fluxoly.com" (Vercel, projeto próprio)
                                                        │  - job 20/20min: snapshot Geral + snapshot Estoque
                                                        │  - KV: snapshots + reservas
                                                        │  - /api: sessão (2 senhas), dados por papel, reservar
                                                        ▼
                                                     Navegador (vendedor / organizador)
   Fluxoly-plataforma (Flask+SQLite, Render/Vercel)  ──  SEM relação, sem credencial compartilhada
```

## Alternativas avaliadas

### Questão 1 — Onde o app vive

| Opção | Prós | Contras | Veredito |
|---|---|---|---|
| **A. Rota no app React/Flask do Fluxoly** | Auth e deploy já existem | Puxa uma 2ª integração MercadoPhone e uma superfície nova para dentro do monólito; a fonte de dados nem é o banco do Fluxoly; ADR-010 pesado sobre `app.py` | ❌ |
| **B. App standalone, pasta no mesmo repo** (`apps/lista-aparelhos-disponiveis/`), deploy Vercel próprio | Isolado; CI/convenções do repo reaproveitadas; um lugar só para a equipe | Introduz um 2º runtime/toolchain no repo | ✅ **escolhida** |
| C. Repositório separado | Isolamento máximo | Mais um repo para gerenciar, permissões, CI duplicado | ❌ (over-kill para o tamanho) |

### Questão 2 — Como impor o acesso de 2 níveis

| Opção | Veredito |
|---|---|
| Senha checada no JavaScript da página estática | ❌ — senha e token visíveis no *view-source*; impossível esconder custo/PII do papel "geral" |
| Vercel Password Protection (proteção nativa de deployment) | ❌ — **uma** senha só por deployment; não separa Geral de Estoque |
| **Função serverless `/api/session`**: valida a senha contra env var → cookie assinado (HMAC) com `role: geral\|estoque`; dados de cada papel servidos só por endpoint autenticado | ✅ **escolhida** — o snapshot "estoque" (com custo) **nunca** é um arquivo estático; só sai por `/api/inventory` quando o cookie diz `role=estoque` |

### Questão 3 — Fonte e atualização

- **API nova** como caminho principal (self-describing, sem depender de export manual). O `.xls` do
  MercadoPhone fica como *fallback* manual documentado, não no fluxo normal.
- **Snapshot**, não proxy ao vivo: um job a cada 20 min (BR-075/QA-28) busca o inventário inteiro,
  aplica os filtros (BR-074/075), deduplica por IMEI (BR-072), calcula o identificador curto (BR-073) e
  grava **dois** documentos com **allowlist de campos** (BR-070/071). Servir ao vivo a cada visita
  gastaria a cota da API e exporia latência/erros da API ao usuário final.

### Questão 4 — Onde mora o estado (snapshots + reservas)

| Opção | Veredito |
|---|---|
| Commit dos JSON no git a cada 20 min | ❌ — polui histórico, corrida com deploys |
| Serviço próprio no Render + Postgres/SQLite | ❌ — infra desproporcional para "uma lista de IMEIs reservados" |
| **Vercel KV** (Redis gerenciado) para os 2 snapshots **e** para o set de reservas | ✅ **escolhida** — sem servidor novo, transacional o suficiente, no mesmo projeto Vercel |

### Questão 5 — Linguagem do runtime

O Fluxoly é Python-first, mas este app **não compartilha código** com ele. Vercel KV, Vercel Cron e as
serverless functions são JS-nativos. **Decisão:** funções serverless e job em **JavaScript/TypeScript**;
página em **HTML/CSS/JS puro** (sem framework — a referência Skyline mostra que a UI não precisa). O
script de `.xls` de fallback, se um dia for necessário, fica em Python (stdlib, como
`scripts/relatorio_comissao_tecnico_mercadophone.py`).

### Questão 6 — Agendamento do job

- **Preferência:** Vercel Cron (`vercel.json` → `crons`), se o plano da conta permitir intervalo
  sub-diário.
- **Fallback:** GitHub Actions `schedule` (`*/20 * * * *`) chamando `POST /api/sync` com um segredo
  compartilhado (`SYNC_SECRET`).

---

## Decisão

Escolhidas: **1-B, 2-serverless, 3-snapshot via API nova, 4-Vercel KV, 5-JS/TS, 6-Vercel Cron (fallback
GH Actions)**.

### Regra explícita de isolamento de credencial (herda o princípio do ADR-012)

- `MERCADOPHONE_API_KEY` vive **exclusivamente** como env var do projeto Vercel `estoque-fluxoly` (e,
  se o fallback de cron for usado, como secret do GitHub Actions **deste repo**). **Nunca** no
  repositório, nunca nos projetos Vercel/Render do Fluxoly-plataforma ou do Demo, nunca no cliente.
- As senhas `SENHA_GERAL` / `SENHA_ESTOQUE` e o `COOKIE_SIGNING_SECRET` seguem a mesma regra.
- O token foi exposto em texto puro no chat durante a Discovery → **rotacionar no MercadoPhone após o
  primeiro deploy** (rastreado em [[project_pending_gemini_key_rotation]] como precedente de processo).

### Definition of Done da arquitetura

1. Projeto Vercel `estoque-fluxoly` criado, domínio `estoque.fluxoly.com`, isolado dos projetos do Fluxoly.
2. Vercel KV provisionado e ligado só a esse projeto.
3. `/api/session` emite cookie assinado com papel; middleware bloqueia as páginas sem cookie válido.
4. `/api/inventory` devolve o snapshot do papel do cookie — o snapshot "estoque" nunca acessível como asset estático.
5. Job de sync roda a cada ~20 min e grava os 2 snapshots no KV, com allowlist de campos verificada por teste.
6. `/api/reservar` e `/api/desreservar` exigem `role=estoque`.
7. Nenhuma env var, credencial ou binding compartilhado com os projetos Render/Vercel do Fluxoly.

## Consequências

### Positivas
- O monólito Fluxoly não ganha superfície nem dependência nova.
- Custo/PII do MercadoPhone nunca alcançam o papel "geral" nem o navegador de quem não é estoque.
- Deploy, credencial e domínio isolados — um problema aqui não atinge produção.

### Negativas / trade-offs aceitos
- Um 2º toolchain (JS/TS + Vercel KV) no repo, num time Python-first — mitigado por ser pequeno e sem acoplamento.
- Mais uma credencial de terceiro (a `X-API-Key`) para gerenciar e rotacionar.
- Dados com até ~20 min de atraso — aceito na Discovery (QA-28); a reserva manual cobre o caso "já vendido" na janela.
- Senha compartilhada por área (não login individual) — aceito para ferramenta interna; quem tem a senha de estoque pode reservar/desreservar.

### Condições de revisão
- Se a ferramenta passar a precisar de login individual, auditoria de quem reservou o quê, ou de
  escrever de volta no MercadoPhone → reabrir (provável migração para dentro do Fluxoly).
- Se a loja migrar o estoque do MercadoPhone para o próprio Fluxoly → a fonte de dados muda e este ADR é substituído.
